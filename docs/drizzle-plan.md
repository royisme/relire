# Drizzle for the content service's D1 (step RS4)

Plan of record. Written 2026-10-24 on the owner's instruction. **Baseline explicitly superseded:** the lexicon tables, the version seed and the importer no longer exist (`docs/lexicon-bundle-plan.md`); the plan stays PAUSED and must be re-baselined on the remaining tables, graded readers, vocabulary book and grammar topics, before resuming. **Owner decision (2026-10-24): option B.** Review 1 (gpt-6-astra, verdict fail, eight problems) is applied below; the reviewer's own recommendation was option A (not worth the dependency for thirteen simple reads), and the owner has chosen B knowing that. Nothing here is built. `docs/remote-settings-plan.md` "Not in this plan" required this plan to say what Drizzle buys against a new dependency before any code; sections 2 and 3 do that, and section 3 ends in a recommendation the owner decides.

## Facts (read 2026-10-24)

- **Schema.** Four migrations, 56 lines in all, hand-written: `0001_init.sql` (`topics`, `meta`, and the seed row `meta('packVersion','0.0.0')`), `0002_lexicon.sql` (`lexicon_entries`, `lexicon_forms`, the `lexiconVersion` seed and indexes), `0003_vocabulary.sql` (`vocabulary_pages`, composite primary key, `CHECK (page >= 0)`), `0004_readers.sql` (`readers`). `worker/wrangler.jsonc` sets `migrations_dir: "migrations"`. Nothing is deployed and no remote database exists.
- **Worker reads.** Thirteen `prepare(...).bind(...)` sites in `worker/src/topics.ts` (4), `lexicon.ts` (3), `vocabulary.ts` (3) and `readers.ts` (3): four use `all()`, nine use `first()`; each is a single-table `SELECT` with at most one `ORDER BY`, none has a SQL `LIMIT`, and the reader existence check selects a constant. Row types are hand-written generics at the call sites (`first<{ body: string }>()`).
- **Publishers.** Topics (`scripts/grammar-topics/publish.ts`) and the lexicon (`scripts/lexicon/import.ts`) generate SQL **text** applied with `wrangler d1 execute --file` (`d1ExecuteSpawn`): the lexicon batches multi-row `INSERT`s of about 50 KB (`import.ts:18,27`); topics emit one uncapped `INSERT` per topic (`publish.ts:27,39`), so the 50 KB figure is a lexicon batching choice, not a shared enforced limit. Vocabulary (`scripts/vocabulary/publication.ts`) and readers (`scripts/graded-readers/publication.ts`) run `INSERT OR IGNORE` / `ON CONFLICT ... DO UPDATE` through a `getPlatformProxy` binding with `DB.prepare(...).bind(...)`. Most publisher protocol tests use Bun SQLite and some run a real local Wrangler/proxy in a temp root, so a publisher column that is missing or renamed against the migrations already fails a test today. They do not prove schema equivalence: dropping the page `CHECK` or the reverse-lookup index would leave valid-fixture tests green.
- **Worker tests.** `tests/fixtures/workerDb.ts` fakes the D1 binding over `bun:sqlite` and implements only `prepare().bind().all()` and `.first()`, loading the four migration files by name (`0001_init.sql` ... `0004_readers.sql`). `tests/d1Target.test.ts` copies `worker/migrations/0001` to `0004` into a temp root, and `tests/gradedReaderRemotePublish.test.ts` (around line 258) lists them too: three hard-coded lists in all.
- **Primary keys.** `topics.id` and `meta.key` are `TEXT PRIMARY KEY` without `NOT NULL`, which SQLite allows to hold NULL; the comparison project's Drizzle `.primaryKey()` emits `PRIMARY KEY NOT NULL` (`my-tanstack-app/drizzle/0000_silly_mongu.sql:2`). A regenerated schema would therefore be stricter than today's.
- **The other project already does this.** `my-tanstack-app` uses `drizzle-orm` ^0.45.3 with `drizzle(env.DB)` from `drizzle-orm/d1`, `drizzle-kit` ^0.31.11 (`drizzle.config.ts`: `schema: ./src/server/schema.ts`, `out: ./drizzle`, `dialect: sqlite`), generated files `0000_silly_mongu.sql` plus a `meta/` folder, and wrangler's `migrations_dir: "drizzle"` pointing at it. So generated migrations coexisting with `wrangler d1 migrations apply` is proven there. Its own unit tests never fake the Drizzle/D1 chain.
- **Not verified here (spike gates):** `drizzle-orm` is not installed in this repo. How the D1 driver calls the binding (it very likely uses `raw()` and `run()` as well as `all()`, which the Worker test fake does not implement); the bundle-size cost in the Worker; whether `drizzle-kit generate` can express every statement of the four migrations (composite primary key, `CHECK`, indexes) and the seed `INSERT`s (it cannot generate data, only a custom migration can carry them); D1's cap on bound parameters per query (believed to be 100; not read from Cloudflare's current documentation), which matters if any multi-row insert moved to a builder.

## What Drizzle would give, and what it would not

Gives:
1. **The schema in one TypeScript file.** Today the table shapes live in four SQL files, in the publishers' column lists and in hand-written row generics; a rename touches all of them.
2. **Typed reads in the Worker.** The thirteen queries return rows typed from the schema instead of hand-annotated generics; a misspelt column fails `tsc`. Inferred types do not validate stored JSON or a live database's real schema.
3. **Generated migrations**, with the `meta/` snapshot for later diffs, the same tool and workflow as `my-tanstack-app` (a shared tool, not a shared schema).

Does not give:
- **Safer publishing.** The SQL-text publishers cannot use the query builder (they emit files for `wrangler d1 execute --file`). The two proxy publishers could, and typed writes would be a benefit, but their current `INSERT OR IGNORE` and `ON CONFLICT` forms are already tested, and a move would need new batching for the lexicon-sized cases; option C stays out for scope and cost, not because of an inherent parameter cap (their page and artifact inserts bind only four or five values).
- **Fewer lines.** It adds a dependency (`drizzle-orm` in `worker/`, `drizzle-kit` as a dev dependency), a schema file, a config file and a test-fake extension, to replace thirteen small queries.
- **A change to the HTTP contract.** Responses, ETags and statuses must stay byte-identical. The Worker's driver and bundle do change.

## Options and recommendation

- **A. Do not adopt Drizzle.** Keep hand-written SQL. Cost: none. Loses the typed reads and the shared schema file with `my-tanstack-app`.
- **B. Minimal adoption (recommended if the owner wants Drizzle).** `worker/src/schema.ts` as the single schema; regenerate migrations from it (allowed: nothing is deployed, AGENTS.md forbids migrations for unreleased states); the Worker's thirteen reads move to Drizzle; **publishers and their SQL stay exactly as they are**. The existing publisher tests then prove the schema and the publishers still agree.
- **C. Full adoption.** B plus the two proxy publishers on the builder. Not recommended: typed writes are the only extra benefit, it needs new batching, and the remote publishers are the code least safe to churn before a first deployment (they have never touched a remote database).

The recommendation, stated plainly: the gain is real but modest, and A is a legitimate answer; the reviewer recommends A. **The owner chose B** (2026-10-24), so B proceeds through the spike below, which ends in "do not ship" if its cost proves larger than the plan assumes.

## Design (option B)

- `worker/package.json`: `drizzle-orm` (exact version) as a dependency, `drizzle-kit` as a dev dependency, a `db:generate` script. `worker/drizzle.config.ts`: `schema: './src/schema.ts'`, `out: './migrations'`, `dialect: 'sqlite'`. `worker/wrangler.jsonc` keeps `migrations_dir: "migrations"`.
- `worker/src/schema.ts`: `sqliteTable` definitions for `topics`, `meta`, `vocabulary_pages` (composite primary key and `check('page >= 0')`), `readers`, with the same column names, types, nullability, primary keys and indexes as today.
- **Migrations regenerated, not appended.** The three hand-written files are replaced by one generated DDL migration plus one custom migration (`drizzle-kit generate --custom`) holding the seed row (`packVersion` = `0.0.0`).
- **Equivalence is a one-off spike comparison, not a permanent legacy fixture.** Against the pre-change revision (`git show 27a684a:worker/migrations/...`), apply old and new sets to two empty databases and compare **logically**: for every table, `PRAGMA table_info` (name, type, notnull, default, pk position), `PRAGMA index_list`/`index_info`, and constraint behaviour (inserting a page `-1` into `vocabulary_pages` fails; a duplicate composite key fails), plus the two seed rows; migration bookkeeping tables excluded. Raw `sqlite_master` text is not compared (quoting and constraint placement differ). The one expected difference is the primary-key `NOT NULL` on `topics.id` and `meta.key`; it is listed and accepted by the owner in the spike report (stricter, no data effect), or the schema is written to preserve nullability if the owner prefers. The result is recorded in the report. **The test that survives RS4b** checks the invariants of the new schema only (tables, columns, primary keys, the index, the `CHECK`, the seeds), with no legacy fixture.
- **Local databases.** A renamed baseline migration fails on an existing local D1 (Wrangler records applied file names, and the tables exist), including the database RS3's dev server shares (`worker/.wrangler/state/v3`). **Owner decision before RS4b lands:** delete `worker/.wrangler/state` and re-run migrations and the local publishers (`grammar-topics/publish.ts --apply-local`, `vocabulary/publish.ts --apply-local-unreviewed`, readers if any). No agent deletes it; no compatibility step is added (AGENTS.md: nothing has shipped).
- **Worker reads** use `drizzle(env.DB)`; the resource functions keep their signatures and return the same `{ body, version }`/error shapes; `ORDER BY` clauses and `LIMIT`s are unchanged. Hono routes, middleware and auth are not touched.
- **Test fake.** Keep the D1-shaped fake over `bun:sqlite` and extend `tests/fixtures/workerDb.ts` only as far as the Drizzle D1 driver needs (`raw()`, `run()` as the spike finds). If that grows beyond a few lines, the spike stops with "do not ship"; the Worker tests must keep exercising the production `D1Database` interface, so no Bun-SQLite Drizzle adapter and no injection seam.
- **Migration references.** The three hard-coded lists (`tests/fixtures/workerDb.ts:15`, `tests/d1Target.test.ts:30`, `tests/gradedReaderRemotePublish.test.ts:258`) become one test-only helper that reads `worker/migrations/*.sql` in sorted order and skips `meta/`. `scripts/content-service/d1Target.ts` and both CI workflows hold no migration file names. Live docs to update: `worker/README.md:97`, `docs/adr-hosted-content-service.md:64`; older mentions in `docs/d-remote-plan.md`, `docs/grammar-order-plan.md`, `docs/vocabulary-flashcards-spec.md` are marked historical, not rewritten.
- **Formatting of generated files.** `worker/migrations/meta/*.json` (snapshots, journal) are generated: add them to `.oxfmtrc.json` `ignorePatterns` instead of hand-formatting (the shape check does not scan SQL or JSON).
- Nothing else changes: `scripts/*/publish*.ts`, `d1Target.ts`, the response bodies, the access key, the runbook commands (`wrangler d1 migrations apply DB --local|--remote` still applies the directory).

## Steps

- **Approval and installs.** The owner has approved the dependency experiment by choosing B. **The lead provisions the installs** (`bun add` of `drizzle-orm`/`drizzle-kit` in the spike worktree's `worker/`, no `node_modules` symlink there, never touching the main checkout); the worker never runs `bun install` or touches the network (RULES.md). The spike then runs offline.
- **RS4a Spike (no commit unless all gates pass).** In that worktree: write `schema.ts`; run `drizzle-kit generate` and show the SQL; apply it with `wrangler d1 migrations apply DB --local` into a temp state dir; compare `sqlite_master`/`PRAGMA table_info` with a database built from the four current files (must be identical apart from the order of statements and Drizzle's naming of indexes, which are listed); convert `topics.ts` only and show what the D1 driver calls on a fake binding; measure the Worker bundle size before and after (`wrangler deploy --dry-run --outdir`, no login, no remote); read Cloudflare's bound-parameter limit. Gates: (1) every statement expressible or covered by the custom migration; (2) the logical comparison above shows no difference except the listed primary-key `NOT NULL`; (3) the fake needs at most a few lines and the existing access-key, ETag and 304 Worker tests pass unchanged in their response expectations; (4) no remote command was needed; (5) the selected versions, licenses, install cost (time and size of `worker/node_modules`) and the raw and gzip Worker bundle delta are recorded and the **owner accepts that cost** (recording a number alone cannot reject a dependency); (6) `bun run dev` serves an authorized `/v1/topics` read from disposable migrated state through Hono and the Vite plugin (a started server is not enough); (7) the updated `worker/bun.lock` passes `bun install --cwd worker --frozen-lockfile`, and root and Worker typechecks, oxlint and oxfmt exit 0. A failing gate ends in "do not ship" with the evidence.
- **RS4b Wire (option B).** Only after RS4a passes and the owner accepts its recorded cost: `schema.ts`, regenerated migrations, the thirteen reads, the test fake, the migration-listing helper, `worker/README.md` and `docs/development.md` lines about migrations, `docs/architecture.md`, the `.oxfmtrc.json` ignore, and the owner's local-state reset above. Acceptance: every existing Worker test passes unchanged in its response expectations; the new-schema invariants test passes; the publisher tests, `d1Target.test.ts`, Worker typecheck, full suite, build and the CI `--check`s exit 0 in the main checkout; `dist` content hash unchanged.
- The lead writes docs, `TASKS.md`, `PROGRESS.md` and any `CHANGELOG.md` line (none expected: nothing a learner can notice). Each worker diff gets a review.

## Risks

- A generated migration name (`0000_adjective_noun.sql`) is random and appears in `wrangler`'s `d1_migrations` table once applied to any database, local or remote; regenerating afterwards breaks that history. So this must land **before** the first remote migration, and the owner resets local state once. If RS4 is not wanted before the first deployment, choose A and never regenerate later.
- A dev dependency pulling a second SQLite/driver stack into `worker/node_modules` (CI runs `bun install --cwd worker --frozen-lockfile`): measure install time in the spike.
Drizzle's `$inferSelect` types for `INTEGER`/`TEXT` columns that store JSON strings stay `string`; no behaviour change, but do not add JSON column modes (the Worker parses bodies itself).
