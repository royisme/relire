# Remote publication of the content service (D-remote, D-origins)

> **Superseded in part (2026-10-24):** the lexicon left the content service (`docs/lexicon-bundle-plan.md`, LB1 to LB3). Every mention below of the lexicon's publisher (`scripts/lexicon/import.ts`), its remote apply, its read-only check, "day 2" and the 49,238 rows is history; the first deployment is one day (topics, vocabulary, readers).


Status: draft for review (2026-10-24), revised after two Argon reviews (both fail; the findings the lead verified against the code are applied). Owner decision of 2026-10-24 (ADR `docs/adr-hosted-content-service.md`, amendment): the first deployment has no accounts, is public read-only, rate limited and CORS limited; topics, the lexicon, the vocabulary book (`unreviewed`) and non-bundled graded readers go up together. Platform only: no content changes, no deploy by an agent.

## Why

Every publisher has only a local apply path, so nothing can be loaded into a deployed D1. The owner needs one command per publisher that writes to the remote database at least as safely as the local run, run by the owner with their own Cloudflare access. No agent, script default, test or CI job may reach remote D1, log in, deploy or read credentials or env files. Reading the local paths for this plan also turned up hygiene gaps that already exist (env files, stray state, telemetry, logs written outside `root`); they are fixed first.

## Design

1. **Fix the local paths first (all four).** Proxy publishers pass `envFiles: ['.no-env-files']` (a non-empty list naming a file that does not exist, so neither `.dev.vars` nor `.env` is read). Local proxy `persist: { path: <root>/worker/.wrangler/state/v3 }`, remote `persist: false`. Every spawned Wrangler (publishers and test setup alike) gets `WRANGLER_SEND_METRICS=false` and `WRANGLER_HIDE_BANNER=true` in its env and the global flag `--env-file .no-env-files` (a file that does not exist), so no `.env*` is loaded into its `process.env`. The CLI path runs `node --no-warnings -- <root>/worker/node_modules/wrangler/wrangler-dist/cli.js` (not `bunx`, not `.bin/wrangler`: its launcher `bin/wrangler.js:24-31` respawns `node` with the arguments and no `--`, so Node 26 reads `--env-file .no-env-files` itself and exits 9 before Wrangler starts; measured 2026-10-24, and the `--` form ran all four migrations in about 1.7 s), `cwd` `<root>/worker/`, an absolute `--config <root>/worker/wrangler.jsonc` and `--persist-to <root>/worker/.wrangler/state`. Vocabulary and readers take config, persist and failure log from `root`, not `vocabularyRepository`/`repositoryRoot`. Every path derives from `root`, so a test with a temp root is a second local D1 by construction; there is no target object.
2. **Never a stale 200.** The first statement of both SQL files becomes `DELETE FROM meta WHERE key = 'packVersion'` (topics) or `'lexiconVersion'` (lexicon); the new version is still the last statement. Any failed or partial run, local or remote, then serves `500 unavailable`, never truncated content under the old ETag. This does not rely on the import being atomic.
3. **Tiny shared helpers, root-based.** `scripts/content-service/d1Target.ts` holds only: `d1ExecuteSpawn(root, remote, ...)` (binary, args including `--env-file .no-env-files`, cwd, env; callers topics and lexicon, and the test setup's `d1 migrations apply` goes through the same helper, never a bare spawn) and `platformProxyOptions(root, remote)` (callers vocabulary and readers). `remote` is the publisher's own parsed flag. Remote args: `--remote --config <root>/worker/wrangler.deploy.jsonc`; remote proxy options: `{ configPath: <root>/worker/wrangler.deploy.jsonc, remoteBindings: true, persist: false, envFiles: ['.no-env-files'] }`. Two real callers each; if review finds one helper with a single caller, it is inlined.
4. **Remote is reachable only from the owner's terminal.** Each publisher gets a pure `parseArgs(args)`; tests call it for every flag, including the remote ones and refusals. The exported functions (`publish` for topics, `importLexicon`, `publish` for vocabulary, `runPublishRemote`) take an explicit `{ allowRemote = false }` option and throw on any remote flag when it is false; only the `import.meta.main` block passes `allowRemote: true`, and no test passes it. Every remote path (all four) also refuses unless `process.stdin.isTTY && process.stdout.isTTY`, which keeps agent shells, CI and tests out, since Wrangler's own prompt is neither a gate nor an exit-code signal (Facts). Flags: topics and lexicon `--apply-remote`; vocabulary `--apply-remote-unreviewed` only (the deployed book is `unreviewed`; a reviewed remote mode waits for a review), readers `--apply-remote`. `--remote`, mixed flags and vocabulary `--apply-remote` are refused.
5. **Topics and lexicon remote: same file, owner at the keyboard.** The file import runs with `stdin`/`stdout` inherited and no `--yes`, so the owner sees Wrangler's confirmation; the owner's terminal may show failing SQL, which is the owner's own private data on their own machine. The local path keeps `stdin: 'ignore'`. Because "No" also exits 0, success is decided only by the read-only check that follows, never by Wrangler's exit code alone: `d1 execute --command ... --json` (stdout piped and parsed, never echoed; never selects `body` or `data`) compares, for topics, `packVersion` and every `(id, position, content_hash, length(CAST(body AS BLOB)))` with the computed values and UTF-8 byte lengths (the stored `content_hash` is what the SQL wrote, not recomputed from the stored body); for the lexicon, `lexiconVersion` and both row counts. Same check on both targets.
6. **Vocabulary and readers remote: same protocol, other binding.** `publishVocabularyBook` and `publishReaders` are unchanged; only `platformProxyOptions` differs. Bound parameters keep the 108 KB pages out of SQL text. If D1 rejects a page that size, the fallback is D-remote-2b (below), decided only after the owner reads Cloudflare's current limits.
7. **Owner config.** `worker/wrangler.deploy.jsonc` (gitignored) is a copy of the committed file with the real `database_id`, `account_id`, `"remote": true` on `DB` and the deployment `ALLOWED_ORIGINS`. The committed file is never edited.
8. **Load order and budget.** Worst case: index entries count as rows written. Day 1: migrations, topics (93 rows, about 186 with the primary-key index, plus meta), vocabulary (30 pages plus marker and pointer, about 64 with indexes), readers (no-op today); then the read-only checks. Day 2 (a new UTC day): the lexicon alone, 49,238 rows plus index entries, between 93,454 (forms index only) and 98,476 (with the entries primary key), against 100,000. Then `wrangler deploy` and smoke checks. No same-day lexicon rerun. A later lexicon reload deletes and inserts, about twice that, so it does not fit one free-plan day in the worst case. Loading before the deploy means no Worker serves the database while an import runs.
9. **Failure.** Topics/lexicon: with the version row deleted first, a stop at any point serves 500 until a rerun completes; rerun the same command (on another day for the lexicon if the budget is spent). A failed check after a complete import stops with the real error. Vocabulary/readers: a stop leaves staged rows without marker or pointer; the old pointer (or none: `404 book-unavailable`, `404 readers-unavailable`) keeps serving; rerun is idempotent. All four publishers write raw errors to ignored logs under `<root>/.pi-runs/` (new for topics, `grammar-topics/failure.log`, and lexicon, `lexicon/failure.log`, because their SQL and D1 errors can carry private prose) and print one fixed line naming the log. Wrangler's own output in the owner's terminal during a remote import is the exception above.
10. **Hygiene (D-origins).** `.gitignore` gains `worker/wrangler.deploy.jsonc`; `worker/README.md` gets the deployment runbook below with rooted commands; artifacts stay in `.local/`, logs in `.pi-runs/`; no workflow gains a remote step.

## Limits

- The offline proof does not exercise the remote branch. A temp root proves the protocol, the checks and the hygiene through real local Wrangler and miniflare; the remote branch is proven only by exact assertions on the arguments and options. The first real remote run is the owner's.
- Topics and the lexicon are not staged. A reload on a live service serves 500 for that kind until it completes; staging them would need a schema change, not done for the first deployment.
- The lexicon check is aggregate (version and counts); topics are checked on stored hashes and body byte lengths, not on body bytes.
- The remote proxy run needs `wrangler login` or `CLOUDFLARE_API_TOKEN`, `account_id` in the deploy config when the login has several accounts, creates a temporary edge-preview Worker, and registers a random workers.dev subdomain if the account has none.
- Wrangler CLI runs may still check for updates from code paths other than the banner (`cli.js:187700`, `:369277`).
- Public read-only is not access control (ADR section 6); the limiter is approximate (`worker/README.md:21`).
