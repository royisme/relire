# Remote publication of the content service (D-remote, D-origins)

Status: draft for review (2026-10-24), revised after Argon's review (fail; the findings the lead verified against the code are applied). Owner decision of 2026-10-24 (ADR `docs/adr-hosted-content-service.md`, amendment): the first deployment has no accounts, is public read-only, rate limited and CORS limited; topics, the lexicon, the vocabulary book (`unreviewed`) and non-bundled graded readers go up together. Platform only: no content changes, no deploy by an agent.

## Why

Every publisher has only a local apply path, so nothing can be loaded into a deployed D1. The owner needs one command per publisher that writes to the remote database at least as safely as the local run, run by the owner with their own Cloudflare access. No agent, script default, test or CI job may reach remote D1, log in, deploy or read credentials or env files. Reading the local paths for this plan also turned up hygiene gaps that already exist (env files, stray state, telemetry, logs written outside `root`); they are fixed first.

## Design

1. **Fix the local paths first (all four).** Proxy publishers pass `envFiles: ['.no-env-files']` (a non-empty list naming a file that does not exist, so neither `.dev.vars` nor `.env` is read). Local proxy `persist: { path: <root>/worker/.wrangler/state/v3 }`, remote `persist: false`. Every spawned Wrangler gets `WRANGLER_SEND_METRICS=false` and `WRANGLER_HIDE_BANNER=true` in its env. The CLI path uses the binary `<root>/worker/node_modules/.bin/wrangler` (not `bunx`), `cwd` `<root>/worker/`, an absolute `--config <root>/worker/wrangler.jsonc` and `--persist-to <root>/worker/.wrangler/state`. Vocabulary takes config, persist and the failure log from `root`. Every path derives from `root`, so a test with a temp root is a second local D1 by construction; there is no target object.
2. **Never a stale 200.** The first statement of both SQL files becomes `DELETE FROM meta WHERE key = 'packVersion'` (topics) or `'lexiconVersion'` (lexicon); the new version is still the last statement. Any failed or partial run, local or remote, then serves `500 unavailable`, never truncated content under the old ETag. This does not rely on the import being atomic.
3. **Tiny shared helpers, root-based.** `scripts/content-service/d1Target.ts` holds only: `d1ExecuteSpawn(root, remote, ...)` (binary, args, cwd, env; callers topics and lexicon) and `platformProxyOptions(root, remote)` (callers vocabulary and readers). `remote` is the publisher's own parsed flag. Remote args: `--remote --config <root>/worker/wrangler.deploy.jsonc`; remote proxy options: `{ configPath: <root>/worker/wrangler.deploy.jsonc, remoteBindings: true, persist: false, envFiles: ['.no-env-files'] }`. Two real callers each; if review finds one helper with a single caller, it is inlined.
4. **Remote is reachable only from the CLI.** Each publisher gets a pure `parseArgs(args)`; tests call it for every flag, including the remote ones and refusals. The remote branch runs only from the `import.meta.main` path; exported functions that tests call refuse a remote mode. Flags: topics and lexicon `--apply-remote`; vocabulary `--apply-remote-unreviewed` only (the deployed book is `unreviewed`; a reviewed remote mode waits for a review), readers `--apply-remote`. `--remote`, mixed flags and vocabulary `--apply-remote` are refused.
5. **Topics and lexicon remote: same file, owner at the keyboard.** The file import runs with `stdin`/`stdout` inherited and no `--yes`, so Wrangler's own confirmation is a human gate; the owner's terminal may show failing SQL, which is the owner's own private data on their own machine. The local path keeps `stdin: 'ignore'`. After the file, a read-only check through `d1 execute --command ... --json` (stdout piped and parsed, never echoed; never selects `body` or `data`) compares: topics, `packVersion` and every `(id, position, content_hash)` with the computed values (the stored `content_hash` is what the SQL wrote, not recomputed from the stored body); lexicon, `lexiconVersion` and both row counts. Same check on both targets.
6. **Vocabulary and readers remote: same protocol, other binding.** `publishVocabularyBook` and `publishReaders` are unchanged; only `platformProxyOptions` differs. Bound parameters keep the 108 KB pages out of SQL text. If D1 rejects a page that size, the fallback is D-remote-2b (below), decided only after the owner reads Cloudflare's current limits.
7. **Owner config.** `worker/wrangler.deploy.jsonc` (gitignored) is a copy of the committed file with the real `database_id`, `account_id`, `"remote": true` on `DB` and the deployment `ALLOWED_ORIGINS`. The committed file is never edited.
8. **Load order and budget.** Worst case: index entries count as rows written. Day 1: migrations, topics (93 rows, about 186 with the primary-key index, plus meta), vocabulary (30 pages plus marker and pointer, about 64 with indexes), readers (no-op today); then the read-only checks. Day 2 (a new UTC day): the lexicon alone, 49,238 rows plus index entries, between 93,454 (forms index only) and 98,476 (with the entries primary key), against 100,000. Then `wrangler deploy` and smoke checks. No same-day lexicon rerun. A later lexicon reload deletes and inserts, about twice that, so it does not fit one free-plan day in the worst case. Loading before the deploy means no Worker serves the database while an import runs.
9. **Failure.** Topics/lexicon: with the version row deleted first, a stop at any point serves 500 until a rerun completes; rerun the same command (on another day for the lexicon if the budget is spent). A failed check after a complete import stops with the real error. Vocabulary/readers: a stop leaves staged rows without marker or pointer; the old pointer (or none: `404 book-unavailable`, `404 readers-unavailable`) keeps serving; rerun is idempotent. Raw errors go to ignored `<root>/.pi-runs/*` logs; nothing prints prose.
10. **Hygiene (D-origins).** `.gitignore` gains `worker/wrangler.deploy.jsonc`; `worker/README.md` gets the deployment runbook below with rooted commands; artifacts stay in `.local/`, logs in `.pi-runs/`; no workflow gains a remote step.

## Limits

- The offline proof does not exercise the remote branch. A temp root proves the protocol, the checks and the hygiene through real local Wrangler and miniflare; the remote branch is proven only by exact assertions on the arguments and options. The first real remote run is the owner's.
- Topics and the lexicon are not staged. A reload on a live service serves 500 for that kind until it completes; staging them would need a schema change, not done for the first deployment.
- The lexicon check is aggregate (version and counts); topics are exact on stored hashes, not on bodies.
- The remote proxy run needs `wrangler login` or `CLOUDFLARE_API_TOKEN`, `account_id` in the deploy config when the login has several accounts, creates a temporary edge-preview Worker, and registers a random workers.dev subdomain if the account has none.
- Wrangler may still check for updates from code paths other than the banner (`cli.js:184585`, `:187700`, `:369277`).
- Public read-only is not access control (ADR section 6); the limiter is approximate (`worker/README.md:21`).
