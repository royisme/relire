# Storage rules

Data map and lifetimes are in `docs/architecture.md` (Data and persistence).

- Only `src/storage/` touches IndexedDB; `db.ts` owns the schema (stores `articles`, `vocab`, `meta`, `cache`, `audio`, `shadowing`, `units`, `itemStates`, `attempts`; one schema creation at version 1).
- Articles use explicit durable-first operations in `db.ts`: `initializeData` checks `meta.started` inside the seeding transaction, `saveArticle` writes one row, and `restoreMissingArticles` inserts only missing candidates and returns their stored versions. Update React state only after commit; never persist an article-list snapshot. Vocabulary uses row-owned `storage/vocabulary.ts` transactions and `useVocabulary` committed reads; only stats use `usePersist`.
- A new persisted entity needs an owning storage API and backup support in `exportData` / `importData`; use its documented write contract rather than adding whole-store autosave.
- Backups never include API keys. They include prompt edits and, optionally, the vocabulary's audio (`exportProtectedAudio`) and shadowing recordings (`exportShadowing`; a backup without the key keeps existing recordings, `[]` clears them, malformed recordings reject the whole import). The `cache` store is never backed up.
- Only settings needed synchronously at startup live in localStorage (`relire_app_settings_v1`, `relire_prompts_v1`, `relire_lang`, `relire_onboarded`, `relire_theme`, `relire_sidebar` (expanded or collapsed sidebar), `relire_practice_card_pos` (where the learner dragged the practice card), `relire_pronunciation_preferences_v1`, `relire_pronunciation_skipped_v1`). Marker preferences contain only per-source display/layer flags; the skipped list holds only sentence texts whose AI answers failed validation, with the error. Neither holds annotations or a readiness flag, and neither is backed up.
- The app is not released yet, so stored shapes may change freely. After the first release, keep them backwards compatible and bump the IndexedDB version with an `upgrade` step (and add the multi-tab `blocked`/`blocking` handling then).
- Vocabulary rows use `vocabularyKey`, deterministic `word:<key>` ids and one schedule. Introduce only on committed first reveal, as FSRS New with zero observations; rate with original epoch/per-word token/revision and retained semantic outcome/operation id/reviewedAt. The pure synchronous ts-fsrs@5.4.2 scheduler is ready before write transactions; preferences are read inside them. Per-card reset retains history and increments row revision; validate current New memory when row revision exceeds the latest review (or no review exists), otherwise require that review's next schedule. Do not mark or reconstruct historical reset segments. Reset/delete advance that word's retained token. Restore advances the epoch. Never adopt fresh tokens for stale work.
- Backup always pairs `vocab` with `vocabularyMeta` scheduler policy/preferences/days (newPerDay plus integer retentionPercent). Keep policy only in backup metadata, not each history record; each record retains the target actually used. No old scheduler decoder, field stripping/conversion or bulk progress reset; prior unreleased rows/backups with removed strict fields reject. Validate raw data before the restore transaction; replace only `vocabularyPreferences` and `vocabularyDay:` keys, preserve `exerciseReset:*`, vocabulary reset tokens and unrelated meta, and advance local epoch once. Notify committed readers before delayed reload.
- Complete vocabulary content uses one validated `content` cache with the existing 365-day TTL. Await and propagate its transaction commit; no per-page cache, partial book or global answer-cache policy change.
- Audio protection/export qualifies only bookmarked or scheduled learner rows: their word, personal sentences and personal analysis usage-example French. Never unseen catalogue or built-in examples; acquired clips only. Shadowing protection remains separate; other clips are trimmed past `AUDIO_CAP_BYTES`.
- Recordings live only in `storage/shadowing.ts`: a take is saved in one transaction that keeps at most `MAX_TAKES`; an article take checks the article still exists, a passage take checks its unit, stored passage, sentence and captured content. A record has exactly one owner: `articleId`, or `passage: { unitId }` with no `articleId`. Passage keys are disjoint encoded keys from the unit and text only, while article keys stay `articleId|sentence`; unit reset keeps recordings and unit deletion leaves unavailable history. Deleting an article goes through `deleteArticleData` (article and its prose recordings together; units are untouched), deleting a set through `deleteSetData` (units, item states, passage recordings, one transaction), never a whole-library sync.
- Exercise data lives only in `storage/exercises.ts` (with `exerciseAttempts.ts`, `exerciseRows.ts`, `exerciseBackup.ts`, `exerciseEvents.ts`). Checking an item writes its item state and its attempt in one transaction; a failure rejects, and checking an already checked item returns the committed state without a second attempt. `saveUnits(units)` saves one batch (every unit shares a `setId`, a `level`, a `createdAt` and optionally a `setTitle`; no article is involved) in one transaction; collisions reject, never overwrite or adopt an existing row. Prepared IDs survive rejected retries. Never write these stores outside that module except the cascade in `deleteSetData` and the restore in `importData`.
- Topic snapshots use guarded `ensureTopicUnit(preparedUnit, entryResetToken)`, not `saveUnits`: validate and compare the original snapshot token in the units/meta transaction before inserting/adopting the deterministic revision id. Opening a topic writes no exercise row; only the first answer persists it. A stale mounted session cannot re-enable prepared bootstrap. Paired `topicOrigin`/`topicQuestion` metadata and self-contained attempt `topicResult` are validated at save/backup boundaries; topic checks derive their strict deterministic verdict and authored feedback from the stored item. Saved Practice/Mistakes need no service fetch or AI. Backups contain the private snapshot/feedback, not the content cache; restore advances retained reset-token identities, including deleted units, without importing counters from the file.
- Every exercise state write takes the unit's reset token (`getResetToken`, read when the work starts) and is rejected with `StaleResetError` when the token moved. Reset, unit delete, set delete and restore bump it in the same transaction as their change; tokens (`meta`, `exerciseReset:<unitId>`) are bumped, never removed.
- Reset keeps attempts. Deleting a unit keeps attempts. Deleting a set deletes its units and item states (same transaction) but keeps attempts: they carry their own prompt and answer text. Deleting an article touches no unit.
- Backups always include `units`, `itemStates`, `attempts` (no toggle). `importData` validates them with the Zod schemas before opening the transaction; malformed data or dangling references reject the whole restore, an absent key keeps the stored rows, `[]` clears them. `ExerciseUnit.learningArea`, `setId`, `level` and `createdAt` (epoch milliseconds, the same on every unit of a batch) and `CheckedResult.strictAccents` are required on every stored row.
- Units and attempts require explicit `learningArea` from `types/learningArea.ts`, never inferred from type, tag, section or import format. Check snapshots it from the stored unit. Grammar accuracy/adaptive inputs use grammar attempts only, including retained deleted-source history. Import review confirms editable per-unit areas and preserves mixed batches in the same stores. Old unreleased shapes intentionally fail validation; no migration/reset or new store.
- Storage tests (`bun test`) run on `fake-indexeddb`: call `freshDb()` from `tests/fixtures/storage.ts` in `beforeEach` so every test gets a new database.
